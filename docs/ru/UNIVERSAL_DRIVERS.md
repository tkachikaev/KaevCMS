# Универсальные драйверы — этапы 1–2 (JSON + read-only LoginServer)

**Статус: экспериментальная реализация, НЕ активна в рабочих подключениях.** В этой версии мы **не заменяли** рабочие PHP-драйверы. LoginServer/GameServer, регистрация, смена паролей, статистика, замки и игровые награды продолжают работать через существующие классы. Редактора и импорта в админке пока нет. Добавлен отдельный сервис чтения LoginServer по JSON, но он не подключён к реальным gateway/resolver. Нельзя выдавать наличие JSON-файла за доказательство совместимости новой сборки.

## Что поставляется

- `driver-profiles/bundled/login-l2j-mobius.json` — LoginServer L2J Mobius;
- `driver-profiles/bundled/login-l2j-mobius-legacy.json` — LoginServer Mobius Legacy C1/C4;
- `driver-profiles/bundled/login-rusacis.json` — LoginServer RUSaCis;
- `driver-profiles/bundled/game-l2j-mobius.json` — GameServer Mobius (включая выбор `karma`/`reputation`);
- `driver-profiles/bundled/game-rusacis.json` — GameServer RUSaCis.

В текущем PHP-коде **один** GameServer-драйвер Mobius, который определяет legacy/modern-схему. Поэтому не создаём фиктивный отдельный GameServer Legacy.

## Формат v1

Каждый профиль содержит `id` (стабильный ключ), `name` (человекочитаемое имя), `type` (`login`/`game`), `format_version: 1`, `config`. Идентичность профиля — пара `type:id`, не имя. В `config` находятся `database` (`dialect`, charset, collation), `requirements` (обязательные и необязательные таблицы/колонки), `capabilities` и карты полей/связей. Драйвер не содержит и не должен содержать параметры реального подключения, SQL, PHP, файловые пути и секреты.

У LoginServer: `accounts.fields`, `accounts.ownership`, разрешённые источники значений `accounts.create.columns`, фиксированный `password.scheme` (`sha1_base64` или `bcrypt_2a` с cost 4–16). При отсутствии записи о пароле допустим профиль только для чтения. Наличие поля `email` в LoginServer не связано с почтой пользователей самой CMS.

У GameServer: `characters.fields` с источниками `column`, `related`, `choice`, `eav` или `operator`; `characters.owner` по логину либо ID; `relations` с `one/many`; `filters` с ограниченными операторами; `rankings` и `features`. Имя таблицы/колонки — строго SQL-идентификатор, а не выражение. Значения сравнений в будущем движке должны передаваться параметрами.

Сложные особенности текущих драйверов **обозначены**, но ещё не исполняются из JSON:

- RUSaCis: `herountil` плюс активный герой в `heroes`, фильтр `deletetime IS NULL OR = 0`;
- Mobius: предпочтение `karma` либо `reputation` зависит от хроник и структуры;
- имена замков RUSaCis — будущий общий локализуемый справочник Castle ID → название;
- отношения персонаж → аккаунт должны проверяться до любых личных игровых операций;
- таблицы `heroes`/`castle` необязательны, их отсутствие не должно ломать список персонажей.

**Важная граница:** `format_version` описывает JSON-схему, но не версию CMS и не версию игровой сборки. Текущий мигратор принимает только формат 1. Более новые и неизвестные форматы отклоняются до использования. При расширении формата добавляются явные преобразователи; не делается неявная догадка о старых ключах.

## Проверки

Офлайн (PHP без Laravel, `vendor`, игровой БД):

```bash
php tests/Integration/UniversalDrivers/validate-profiles.php
```

Негативные проверки охватывают неправильную структуру/версию, произвольные операторы, дополнительные SQL/PHP-поля, некорректные идентификаторы, размер JSON и несовместимый charset/collation. PHPUnit дополнительно сравнивает **списки колонок** пяти профилей с нынешним `ServerDriverRegistry` и инспекторами схем.

В `.github/workflows/quality.yml` подготовлена отдельная задача с **чистым MySQL 8.4**, тестовыми таблицами, персонажами двух аккаунтов, героями, кланом и замком. Локально запускать только на одноразовом MySQL без данных сайта; скрипт блокирует удалённые хосты и требует явного флага:

```bash
KAEV_UNIVERSAL_MYSQL_TEST=1 KAEV_MYSQL_TEST_HOST=127.0.0.1 \
KAEV_MYSQL_TEST_USER=root KAEV_MYSQL_TEST_PASSWORD='TEST_ONLY' \
php tests/Integration/UniversalDrivers/mysql-fixtures.php
```

MySQL-тест создаёт **уникальные временные базы только для этого запуска**, выполняет проверку игровых фикстур, затем сравнивает результаты **двух read-only путей LoginServer** (новый `UniversalLoginAccountReader` и штатные `MobiusLoginDriver` / `RusacisLoginDriver`) на одинаковых данных. Проверяются `summary` и `inspect`, найденный/отсутствующий аккаунт, неверный пароль/email, попытки SQL-инъекции через значение логина, а также отсутствие опциональных колонок. Базы удаляются после выполнения. Для паритетного теста нужны зависимости из `composer.lock`; в CI они устанавливаются через `composer install`. Не использовать на production MySQL. Формат полей пока считается *проектным контрактом*: допустимость JSON не означает подтверждённую работоспособность каждой карты в игре.

## Будущее

В итерации 2 добавлен **только read-only** `app/Services/GameAccounts/UniversalLoginAccountReader.php`:

- `summary(Connection, profile, login)` — чтение логина, активности, времени создания, блокировки (как в существующих PHP-драйверах);
- `inspect(Connection, profile, PreparedGameAccount)` — сверка записанного хеша и email (если профиль предусматривает email), **без повторного хеширования и записи**;
- `diagnose(Connection, profile)` — перечень отсутствующих обязательных и необязательных таблиц/полей.

Имена SQL-объектов допускаются только после строгой проверки JSON; значение логина передаётся параметром Query Builder. В JSON LoginServer метаданные, не нужные для базовой операции, отделены как `optional_columns`. Отсутствие колонки доступа возвращает `status=unknown`, а не ложное `active`. При отсутствии email в фактической схеме Mobius `inspect` отклоняет сопоставление (fail-closed). Чтение не перехватывает исключения соединения/БД и не объявляет успех при сбое. Адаптер принимает существующее Laravel-подключение MySQL, не создаёт собственного DSN и ничего не знает о production параметрах сервера.

Новый сервис **не активирован** для существующих LoginServer. Универсальные чтения GameServer, записи и конструктор появятся на следующих этапах. Конструктор, редактируемые встроенные профили, пользовательские overrides/tombstones и фиксируемые для подключений снимки — позднейшие итерации. Разделение `database.dialect` оставлено для будущего MS SQL Server / PTS, но `sqlserver` пока отклоняется: его адаптера нет. Зависимости не добавлены, миграций БД не требуется.
