# Универсальные драйверы KaevCMS

## Назначение и границы

В разделе **Серверы → Драйверы** можно создать, скопировать, импортировать и экспортировать JSON-профиль LoginServer или GameServer. Профиль описывает названия игровых таблиц/полей и поддерживаемые функции. Он **не содержит** адреса БД, пароли, произвольный SQL или PHP. Поддерживается MySQL/MariaDB. MS SQL/PTS **не поддерживается**.

**Mobius, RUSaCis и пользовательские драйверы используют единый движок JSON-профилей.** Существующие подключения со штатными идентификаторами продолжают использовать комплектный профиль без перенастройки. Изменение каталога не переключает действующий сервер. Для пользовательского или отредактированного профиля выберите драйвер и примените его через проверку подключения. Для регистрации и смены пароля необходим уникальный индекс логина и колонка достаточной длины для хеша. Применённый профиль хранится как неизменяемый снимок с SHA256 и HMAC-привязкой к реквизитам подключения. После смены реквизитов или редактирования JSON нужна повторная проверка и применение. При изменении реквизитов LoginServer повторно примените JSON также для GameServer, использующих его подключение. CMS не возвращается автоматически к комплектному профилю при ошибке подтверждения; серверы с отдельными реквизитами не требуют повторной проверки из-за этой смены.

## Редактор LoginServer

На первом шаге: название, короткий ID, кодировка/сопоставление, схема игрового пароля, функции. Во втором: таблица аккаунтов, колонки логина, пароля и необязательных данных, фиксированные поля регистрации, поля расширений модулей. Профиль только для чтения позволяет получать сведения об аккаунте без создания или смены пароля. Регистрация и функции кабинета, требующие полного набора операций LoginServer, недоступны на таком подключении. Для записи необходимы логин и пароль, а физическая БД должна иметь **уникальный индекс по колонке логина** и колонку пароля нужной длины. Колонка логина должна быть строковой; числовой столбец не принимается как логин.

Доступные схемы пароля: SHA-1/Base64, BCrypt `$2a$`, SHA-1/MD5/SHA-256/Whirlpool (hex). Они выбираются из фиксированного списка. JSON не разрешает произвольный код. Реальное принятие игровым LoginServer пароля и возможности восстановления повторов проверяются отдельно. Правила регистрации логинов по-прежнему ограничены текущей логикой CMS (не произвольные regex в JSON).

## Редактор GameServer

Три шага: настройки, отображение полей персонажей, связи и статистика. JSON описывает структуру `characters`, связи с кланами, героями и замками, фильтры и рейтинги. **Онлайн** считается по `characters.fields.online`, когда это обычная колонка; для прочих способов хранения статуса счётчик не объявляется автоматически. Применённый снимок имеет приоритет над комплектным описанием таблицы.

Ограничения: рейтинги EAV и сортировка по удалённым полям не поддерживаются; привязка владельца персонажа через внутренний Account ID не активирована для личных операций. Возврат персонажа поддерживается через проверенный JSON с прямыми полями координат и безопасности; подробности в [руководстве](CHARACTER_RESCUE.md). Поставка очереди наград, кошелька и пожертвований не менялась.

### Связанные поля

Для поля из другой таблицы настройка связи `left` сохраняет персонажа, даже если связанной записи нет: значение поля будет пустым. `inner` требует существования связанной записи; для EAV — записи с каждым настроенным ключом. Значение самой записи может быть NULL. Обязательные связи одинаково ограничивают персонажей в ЛК, рейтингах, списке героев и счётчике персонажей на дашборде. Для `inner` таблица и используемые столбцы должны быть обязательными в требованиях схемы. Связи, используемые только для героев или замков, не исключают обычных персонажей. Возврат персонажа отключается при обязательной связанной записи: запись координат не поддерживает блокировку связанных таблиц. Счётчик онлайна по-прежнему считает подключённых персонажей по полю online.

### Источники рейтингов и фильтров

В рейтингах явно показаны таблица и основной столбец из сопоставлений персонажа. Для уровня рекомендуется дополнительная сортировка по опыту, для PvP/PK/времени — по уровню. Пустая дополнительная сортировка не отключает рейтинг. Окончательный порядок при равенстве — по имени. Источники рейтингов пока ограничены прямыми столбцами основной таблицы.

Фильтр задаётся цепочкой «Таблица → Столбец → Условие → Значение». Для другой таблицы обязательны два столбца связи: в основной таблице и в таблице фильтра. Например, `characters.obj_Id ↔ character_access.char_id`. Связь проверяется через `EXISTS`: повторяющиеся записи не дублируют персонажа, а отсутствие подходящей записи исключает его. Условия одной таблицы с одинаковыми ключами должны совпасть в одной записи. Это позволяет, например, отбирать EAV-запись одновременно по ключу и значению.

Все фильтры объединяются через AND и применяются к публичным спискам, персонажам в ЛК и счётчику персонажей на дашборде администратора. Настройка `accesslevel = 0` скрывает GM также в ЛК. Для `zero_or_null` отдельное значение не задаётся. Новые профили могут содержать `filters[].table` и `filters[].link = {local_column, foreign_column}`; без `table` сохраняется прежний источник — основная таблица. Старые версии CMS могут отклонить новые ключи, поэтому импортировать такой профиль нужно в версию с поддержкой связанных фильтров. При проверке подключения обязательны обе таблицы и все столбцы условия/связи; запросы не меняют игровые данные.

## Кодировка БД

Поля **Charset** и **Collation** редактируются в первом шаге обоих конструкторов. **У активного JSON-снимка они берутся из профиля и имеют приоритет над стандартным полем кодировки подключения.** Чтобы поменять кодировку, отредактируйте JSON-профиль и примените его заново к серверу. Подключения без применённого снимка сохраняют прежнюю кодировку. Некорректная кодировка не должна молча переключать сервер.

## Что проверяется перед применением

Проверка выполняется без записи в игровую БД: соединение, обязательные таблицы/колонки, сопоставления данных. Для аккаунтных операций записи — индекс уникальности логина и пригодная длина колонки пароля. Недоступные рейтинги, герои, замки и возврат персонажа отображаются отдельно в отчёте и не блокируют применение, если обязательные таблицы, колонки и фильтры профиля прошли проверку. Конструктор не делает координаты и поля, используемые только героями или замками, обязательными для всего подключения. Если поле нужно также для идентификации, основного сопоставления или фильтра, оно остаётся обязательным. При отсутствии явно необязательных связанных полей их значения не отображаются, а персонажи остаются доступны. Если таблица или колонка объявлена обязательной, её отсутствие по-прежнему блокирует применение. Тип столбца владельца персонажа должен соответствовать указанному идентификатору: строка для логина, целое число для ID. Неприменённый пользовательский профиль не считается рабочим подключением; обычная диагностика сообщает о необходимости применения. Это **проверка структуры**, а не доказательство успешной игровой регистрации, входа клиентом или всех пользовательских сценариев.

## Модули и `driver_extensions`

Модуль объявляет необходимые параметры в своём `module.json`, администратор задаёт таблицы/поля в разделе «Для модулей» конструктора. Группа расширения с колонками должна иметь **ровно одну** таблицу (`kind: table`); несколько разных таблиц описываются отдельными группами. При включении обязательного расширения CMS проверяет заполненность значений и физическое существование объявленных таблиц и колонок. При чтении значений модулем схема проверяется повторно; если она изменилась, выдаётся пустой ответ. Для пользовательского JSON разрешён **только проверенный, применённый снимок**, а не черновик из каталога. Для штатных подключений без снимка доступен неизменённый комплектный профиль.

Сам модуль обязан использовать безопасный Query Builder, контролировать права, владельца записи и ограничения игровой операции. Проверка существования таблицы **не выдаёт права на запись** и не заменяет бизнес-проверки.

## Проверки и готовность

Автономные тесты без Composer/БД: `php tests/Integration/UniversalDrivers/validate-profiles.php`, `validate-write-profiles.php`, `validate-editor-drafts.php`, `validate-schema-preflight.php`. Полноценная приёмка требует MySQL/MariaDB на отдельной тестовой схеме, PHPUnit, PHPStan, Playwright, испытаний обновления Windows/VDS/shared и сверки игрового клиента.
