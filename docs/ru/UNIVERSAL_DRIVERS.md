# Universal drivers — development history / current version 0.53.11

## Как пользоваться редактором

«Сервер авторизации» описывает аккаунты и игровые пароли, «Игровой сервер» — персонажей и статистику. «Изменить» открывает существующий профиль. Для нового драйвера можно выбрать текущую конфигурацию из списка и использовать её как основу несохранённого черновика.

Редактор авторизации состоит из двух шагов. Сначала задайте отображаемое название (любой язык), короткое имя для файла (латиница, цифры и разделители), кодировку, сравнение строк и формат игровых паролей. Короткое имя нового драйвера можно оставить пустым: CMS создаст его из названия. После создания оно неизменно. Затем сопоставьте поля: **данные, нужные сайту → таблица игровой базы → столбец с данными**. Например: «Логин аккаунта → accounts → login». Название таблицы редактируется в любой строке и меняется сразу во всех строках, поскольку аккаунты читаются из одной таблицы.

Логин и пароль обязательны. Остальные поля можно оставить пустыми, если их нет в вашей сборке. Поиск, создание аккаунтов, смена пароля и чтение статуса входят в конфигурацию автоматически; отдельных выключателей нет. При сохранении требования к основной таблице строятся из заполненных полей и дополнительных значений регистрации. Старое имя основной таблицы заменяется новым, правила других таблиц исходного профиля сохраняются. Все указанные столбцы проверяются как обязательные; несуществующие необязательные поля оставляйте пустыми. Столбец связи с аккаунтом выводится из сопоставления логина или ID исходного профиля, без второго ручного ввода. Алгоритмы SHA-1/Base64 и BCrypt `$2a$` реализованы; Whirlpool пока не поддерживается.

Дополнительные значения регистрации нужны только сборкам, требующим заполнения других столбцов при создании аккаунта (например, обычного уровня доступа `accessLevel = 0`). Действуют существующие ограничения: ими нельзя заменить логин/пароль или выдать повышенные права.

Редактор игрового сервера разделён на три шага: настройки, сопоставление полей, связи и статистика. Галочек функций и ручного списка требований к схеме нет. Таблицы и столбцы редактируются прямо в строках; требования строятся по используемым данным. Необязательные поля существующего профиля и таблицы героев/замков остаются необязательными. Связанные ключи и вторичная сортировка следуют за переименованием основных полей; явные изменения ключей сохраняются. Рейтинги определяются по прямым полям уровня, PvP, PK и времени игры. Для таблиц характеристик (EAV) доступны данные персонажей, но общие рейтинги и список героев пока недоступны; это отражается в интерфейсе и возможностях профиля. Перенос застрявшего персонажа через JSON-драйвер не включается. Сохранение любого драйвера в каталог не подтверждает совместимость с реальной базой и не применяет его к серверу. Проверка и применение выполняются отдельно в настройках подключения.

## Итерация 8 — подключение к CMS (0.53.10)

**Текущий статус: экспериментальный.** Профили из каталога доступны для выбора при создании LoginServer/GameServer. Пользовательские драйверы подключаются только после успешной проверки реальной MySQL-схемы. Для ранее существовавших RUSaCis/Mobius PHP-драйверы остаются активными, пока администратор вручную не нажмёт **«Применить JSON и проверить»**. При ошибке прежний профиль не заменяется.

Успешная проверка сохраняет снимок JSON для конкретного подключения с SHA256 и привязкой HMAC к параметрам БД; изменение каталога не меняет активный снимок. Если реквизиты подключения меняются, проверку необходимо пройти повторно. Для новых профилей применяются настоящие ограничения SQL: никакого произвольного SQL/PHP, пока только MySQL/MariaDB, пароль SHA-1/Base64 или BCrypt `$2a$`.

**Границы:** идентификаторы персонажей по внутреннему ID аккаунта пока запрещены для персональных операций, пока не реализована проверка LoginServer ID → GameServer owner. У JSON-профилей не работает старый Mobius rescue, потому что его SQL жёстко привязан к структуре Mobius. Доставка через очередь игровых наград, кошелёк и пожертвования не менялись. Совместимость с конкретным GameServer и обработка паролей игровым LoginServer должны подтверждаться отдельно.

**Миграция:** `2026_10_25_020000_bind_universal_snapshots_to_connections.php` добавляет одну колонку в таблицу снимков CMS, не трогая игровую БД и прежние опубликованные миграции.

**Перед production:** через Codex/CI запустить PHPUnit, PHPStan, миграции, MySQL parity, Windows quality и браузерные проверки. Не переходить массово на JSON до завершения проверок и этапа 9.

# Универсальные драйверы — этапы 1–3 (JSON + read-only LoginServer/GameServer)

**Статус: экспериментальная реализация, НЕ активна в рабочих подключениях.** В этой версии мы **не заменяли** рабочие PHP-драйверы. LoginServer/GameServer, регистрация, смена паролей, статистика, замки и игровые награды продолжают работать через существующие классы. Редактора и импорта в админке пока нет. Добавлены отдельные сервисы чтения LoginServer и персонажей GameServer по JSON, но он не подключён к реальным gateway/resolver. Нельзя выдавать наличие JSON-файла за доказательство совместимости новой сборки.

## Что поставляется

- `driver-profiles/bundled/login-l2j-mobius.json` — LoginServer L2J Mobius;
- `driver-profiles/bundled/login-l2j-mobius-legacy.json` — LoginServer Mobius Legacy C1/C4;
- `driver-profiles/bundled/login-rusacis.json` — LoginServer RUSaCis;
- `driver-profiles/bundled/game-l2j-mobius.json` — GameServer Mobius (включая выбор `karma`/`reputation`);
- `driver-profiles/bundled/game-rusacis.json` — GameServer RUSaCis.

В текущем PHP-коде **один** GameServer-драйвер Mobius, который определяет legacy/modern-схему. Поэтому не создаём фиктивный отдельный GameServer Legacy.

## Формат v1

Каждый профиль содержит `id` (стабильный ключ), `name` (человекочитаемое имя), `type` (`login`/`game`), `format_version: 1`, `config`. Идентичность профиля — пара `type:id`, не имя. В `config` находятся `database` (`dialect`, charset, collation), `requirements` (обязательные и необязательные таблицы/колонки), `capabilities` и карты полей/связей. Драйвер не содержит и не должен содержать параметры реального подключения, SQL, PHP, файловые пути и секреты.

У LoginServer: `accounts.fields`, `accounts.ownership`, разрешённые источники значений `accounts.create.columns`, фиксированный `password.scheme` (`sha1_base64` или `bcrypt_2a` с cost 4–16). При отсутствии записи о пароле допустим профиль только для чтения. Наличие поля `email` в LoginServer не связано с почтой пользователей самой CMS.

У GameServer: `characters.fields` с источниками `column`, `related`, `choice`, `eav` или `operator`; `characters.owner` по логину либо ID; `relations` с `one/many`; `filters` с ограниченными операторами; `rankings` и `features`. Имя таблицы/колонки — строго SQL-идентификатор, а не выражение. Значения сравнений передаются параметрами в экспериментальных сервисах чтения.

Особенности текущих драйверов; часть уже исполняется в экспериментальном чтении персонажей:

- RUSaCis: `herountil` плюс активный герой в `heroes`, фильтр `deletetime IS NULL OR = 0`;
- Mobius: предпочтение `karma` либо `reputation` зависит от хроник и структуры;
- имена замков RUSaCis — будущий общий локализуемый справочник Castle ID → название;
- отношения персонаж → аккаунт должны проверяться до любых личных игровых операций;
- таблицы `heroes`/`castle` необязательны, их отсутствие не должно ломать список персонажей.

**Важная граница:** `format_version` описывает JSON-схему, но не версию CMS и не версию игровой сборки. Текущий мигратор принимает только формат 1. Более новые и неизвестные форматы отклоняются до использования. При расширении формата добавляются явные преобразователи; не делается неявная догадка о старых ключах.

## Проверки

Офлайн (PHP без Laravel, `vendor`, игровой БД):

```bash
php tests/Integration/UniversalDrivers/validate-profiles.php
```

Негативные проверки охватывают неправильную структуру/версию, произвольные операторы, дополнительные SQL/PHP-поля, некорректные идентификаторы, размер JSON и несовместимый charset/collation. PHPUnit дополнительно сравнивает **списки колонок** пяти профилей с нынешним `ServerDriverRegistry` и инспекторами схем.

В `.github/workflows/quality.yml` подготовлена отдельная задача с **чистым MySQL 8.4**, тестовыми таблицами, персонажами двух аккаунтов, героями, кланом и замком. Локально запускать только на одноразовом MySQL без данных сайта; скрипт блокирует удалённые хосты и требует явного флага:

```bash
KAEV_UNIVERSAL_MYSQL_TEST=1 KAEV_MYSQL_TEST_HOST=127.0.0.1 \
KAEV_MYSQL_TEST_USER=root KAEV_MYSQL_TEST_PASSWORD='TEST_ONLY' \
php tests/Integration/UniversalDrivers/mysql-fixtures.php
```

MySQL-тест создаёт **уникальные временные базы только для этого запуска**, выполняет проверку игровых фикстур, затем сравнивает результаты **двух read-only путей LoginServer** (новый `UniversalLoginAccountReader` и штатные `MobiusLoginDriver` / `RusacisLoginDriver`) на одинаковых данных. Проверяются `summary` и `inspect`, найденный/отсутствующий аккаунт, неверный пароль/email, попытки SQL-инъекции через значение логина, а также отсутствие опциональных колонок. Базы удаляются после выполнения. Для паритетного теста нужны зависимости из `composer.lock`; в CI они устанавливаются через `composer install`. Не использовать на production MySQL. Формат полей пока считается *проектным контрактом*: допустимость JSON не означает подтверждённую работоспособность каждой карты в игре.

## Будущее

В итерации 2 добавлен **только read-only** `app/Services/GameAccounts/UniversalLoginAccountReader.php`:

- `summary(Connection, profile, login)` — чтение логина, активности, времени создания, блокировки (как в существующих PHP-драйверах);
- `inspect(Connection, profile, PreparedGameAccount)` — сверка записанного хеша и email (если профиль предусматривает email), **без повторного хеширования и записи**;
- `diagnose(Connection, profile)` — перечень отсутствующих обязательных и необязательных таблиц/полей.

Имена SQL-объектов допускаются только после строгой проверки JSON; значение логина передаётся параметром Query Builder. В JSON LoginServer метаданные, не нужные для базовой операции, отделены как `optional_columns`. Отсутствие колонки доступа возвращает `status=unknown`, а не ложное `active`. При отсутствии email в фактической схеме Mobius `inspect` отклоняет сопоставление (fail-closed). Чтение не перехватывает исключения соединения/БД и не объявляет успех при сбое. Адаптер принимает существующее Laravel-подключение MySQL, не создаёт собственного DSN и ничего не знает о production параметрах сервера.

Новые сервисы **не активированы** для рабочих LoginServer/GameServer. Рейтинги, записи и конструктор появятся на следующих этапах. Конструктор, редактируемые встроенные профили, пользовательские overrides/tombstones и фиксируемые для подключений снимки — позднейшие итерации. Разделение `database.dialect` оставлено для будущего MS SQL Server / PTS, но `sqlserver` пока отклоняется: его адаптера нет. Зависимости не добавлены, миграций БД не требуется.


## Итерация 3 — экспериментальный read-only GameServer (0.53.5)

Добавлен `app/Services/GameWorld/UniversalGameCharacterReader.php`, который принимает **уже существующее** подключение Laravel MySQL, проверенный JSON и доверенный идентификатор игрового аккаунта. Он не является публичным API, не выбирает игровой сервер самостоятельно и не связан с действующим `GameWorldDriverResolver`. Перед показом персональных данных вызывающий код должен подтвердить права пользователя и владение игровым аккаунтом.

- `diagnose(Connection, profile)` — диагностирует отсутствующие обязательные/необязательные таблицы и колонки до чтения.
- `charactersForAccount(Connection, profile, identity, limit, chronicle)` — читает персонажей строго по `characters.owner`, применяет привязанные фильтры, нормализует прямые, `choice`, связанные и EAV-поля, после чего сортирует по уровню и имени и ограничивает ответ 1–100 строками.
- Поддержаны заранее разрешённый оператор героя RUSaCis (`herountil` и активная запись в `heroes`), выбор `karma/reputation` у Mobius по хронике и необязательные игровые поля.
- Связанные поля выполняются пакетными SELECT-запросами без произвольных JOIN/SQL из JSON. При нескольких связанных строках вместо одной или двух EAV-значениях для одного ключа чтение завершается ошибкой; значения EAV привязываются параметрами.
- Ограничение на количество прочитанных строк аккаунта — 1000; превышение приводит к явной ошибке, чтобы не дать неограниченный скан и не показывать неполные данные. Эту границу нужно пересмотреть при появлении серверов с необычно большим числом персонажей на аккаунт.

**Не реализовано в этой итерации:** переключение рабочих GameServer, рейтинги PvP/PK/level, списки героев, владельцы замков, конструктор и операции записи. Они остаются на последующих этапах. Результаты чтения персонажей не подтверждают сами по себе авторизацию пользователя CMS.

В `tests/Integration/UniversalDrivers/mysql-game-character-parity.php` подготовлено сравнение старых PHP-драйверов с новым движком на MySQL 8.4; оно запускается из существующего `mysql-fixtures.php` перед LoginServer-тестами. Проверяются чужие аккаунты, SQL-инъекция, фильтры, выбор колонки по хронике, герой RUSaCis, EAV и отбрасывание неоднозначных связей. Для реального запуска нужен `vendor` и локальный MySQL/MariaDB, согласно команде выше. **До успешного запуска это лишь подготовленные тесты, а не доказанная совместимость.**


## Итерация 4 — экспериментальное чтение рейтингов, героев и замков (0.53.6)

`app/Services/GameWorld/UniversalGameWorldReader.php` реализует независимые read-only методы `ranking`, `heroes`, `castleOwners`, `capabilities` и `diagnose`. Использует переданное уже установленное Laravel MySQL-подключение; не создаёт DSN и **не подключается к действующему GameWorldDriverResolver**. Запись в игровую БД отсутствует.

- Рейтинги `level`, `pvp`, `pk`, `play_time`: сортировка и ограничение 1–100 по заданным в JSON колонкам, фильтрация заблокированных/удалённых персонажей, имя клана из связанной таблицы, безопасные значения через Query Builder. При неоднозначной однострочной связи результат отклоняется, а не смешивается с другим персонажем.
- Герои: отдельный список по ключу персонажа из JSON. У RUSaCis действуют условия `played=1` и `active=1`; у Mobius берутся записи, включая поля `count`, `played`, `claimed`. Вычисляемый флаг героя RUSaCis учитывает `herountil` либо действующую запись `heroes`.
- Замки: настройки связей клан → замок и клан → лидер хранятся в профиле. Источник имени замка — колонка в игре (Mobius) или общий стандартный справочник 9 замков с переводами RU/EN (RUSaCis), неизвестный ID получает `Castle #ID` / `Замок №ID`. Дополнения справочника независимы от конкретного JSON.
- Дополнительные поля `features.heroes.count_column`, `claimed_column` и `features.castles.clan_relation`, `leader_relation`, `clan_columns`, `leader_name_column` являются **необязательными расширениями формата v1**; прежние JSON продолжат проходить проверку, а новые сборки смогут задавать иные имена столбцов без PHP-класса на каждую сборку.
- Отсутствие необязательных таблиц `heroes`/`castle` отключает только соответствующие возможности. Проверка статуса и получение других рейтингов остаются доступны при целостной обязательной схеме.

**Технические ограничения:** сортировка рейтингов по EAV-полям / полям из сторонних таблиц пока не поддерживается; при такой карте возвращается ошибка, а не некорректный рейтинг. Для полной реализации универсального конструктора потребуется отдельный безопасный механизм таких сортировок. Сравнение с существующими драйверами подготовлено в `tests/Integration/UniversalDrivers/mysql-game-world-parity.php` и запускается из `mysql-fixtures.php` в MySQL CI. Пока тест реально не запущен, паритет **не подтверждён**. Подключение живых GameServer не переключено, изменения в БД CMS не требуются.

## Итерация 5 — экспериментальная запись LoginServer (0.53.7)

`app/Services/GameAccounts/UniversalLoginAccountWriter.php` готовит игровой пароль по заранее разрешённой схеме JSON (`sha1_base64` у Mobius/Legacy, BCrypt `$2a$` с указанным cost у RUSaCis), создаёт запись аккаунта и меняет пароль через существующее подключение Laravel **только MySQL**. Никакие маршруты, сервисы регистрации CMS или рабочий `LoginServerDriverResolver` **не переключены**.

- `preparePassword(profile, rawPassword)` и `acceptsCredential(profile, credential)` работают офлайн. BCrypt генерируется единожды перед внешним действием; при восстановлении создания аккаунта используется исходный сохранённый хеш, а не новый BCrypt с другой солью.
- `create(Connection, profile, PreparedGameAccount)` вставляет только разрешённые конфигурацией столбцы с параметрами Query Builder. Поля `login`, `credential`, `email` имеют фиксированные источники. `accounts.create.fixed_values` позволяет указать дополнительные скалярные константы для объявленных в `requirements` колонок, без перезаписи идентификаторов/секретов и без назначения повышенных игровых привилегий. При отсутствии capability, обязательных колонок **или уникального индекса на логине** запись отклоняется.
- `changePreparedPassword(Connection, profile, login, expectedCredential, replacementCredential)` выполняет сравнение и атомарное условное обновление хеша. При повторе **того же подготовленного хеша** можно подтвердить уже выполненную операцию после потери ответа; при стороннем изменении операция отклоняется. Обычная смена пароля через кабинет продолжает использовать прежний драйвер. Для безопасного подключения нового метода в будущем вызывающая подсистема должна сохранять prepared target/expected proof и обеспечивать права пользователя.
- Создание с конфликтом уникальности оставляет SQL-исключение внешнему шлюзу: существующие `GameAccountProvisioner`/`ExternalGameAccountGateway` уже умеют различать `AlreadyExists`, `pending/active/failed`, UUID и recovery. Новый экспериментальный адаптер **не создаёт второй механизм резервирования** и не объявляет успех, если MySQL вернул неопределённый результат.

Автономные проверки: `php tests/Integration/UniversalDrivers/validate-write-profiles.php`. В MySQL CI `mysql-fixtures.php` дополнен `mysql-login-write-parity.php`: пароль, вставка, подтверждение состояния после повторного INSERT, уникальность логина, условная смена пароля, отказ при конкурентном конфликте и отсутствии уникального индекса. **До реального успешного прогона на MySQL паритет записи не доказан.** Реальный вход через LoginServer также требует отдельной проверки на игровой сборке; совпадение формата BCrypt ещё не доказывает приём пароля сервером.

Не входит в итерацию: пользовательский редактор/импорт, новые игровые алгоритмы, MS SQL/PTS, переключение действующих подключений, смена пароля с отдельным журналом идемпотентности в ядре, изменение миграций CMS или обновление зависимостей.

## Итерация 6 — локальный каталог профилей и проверенные снимки (0.53.8)

`DriverProfileCatalog` объединяет пять встроенных JSON из `driver-profiles/bundled` с записями **только в основной БД KaevCMS** (`universal_driver_profiles`). Встроенные файлы остаются собственностью релиза; изменения записываются в локальный override по тому же `type:id`, а удаление встроенного — в tombstone. Обновление CMS не должно удалять эту таблицу и не возвращает скрытый встроенный профиль. Команда `restoreBuiltin` возвращает исходный профиль текущей поставки. Удалить используемый профиль нельзя (проверяются `login_servers`, `game_servers` и проверенные снимки). Импорт JSON не перезаписывает совпавший ID/название, создавая отдельную копию с суффиксом. Экспорт выдаёт только проверенный JSON без реквизитов подключения и секретов.

`ConnectionProfileSnapshots` сохраняет отдельную **после успешной внешней проверки** копию профиля в `universal_driver_connection_snapshots`: JSON, `format_version`, SHA256, идентичность подключения и время проверки. API принимает обязательный callback проверки действительного подключения и схемы. При неудаче предыдущий снимок остаётся неизменным; контроль целостности при чтении обязателен. Простое сохранение каталога никогда не меняет снимок. **Это подготовительная инфраструктура, а не уже включённый процесс проверки/применения в формах сервера**: привязка к действующим маршрутам/проверкам появится на итерациях 7–8. Для старых подключений снимок пока отсутствует; действующий PHP-драйвер остаётся активным.

Миграция `2026_10_25_010000_create_universal_driver_catalog_tables.php` только **добавляет две таблицы в БД CMS**, не изменяя игровые БД, пользователей или существующие таблицы подключений. Локальная конфигурация не должна попадать в релизный ZIP. На штатной установке/обновлении миграция выполняется обычным механизмом CMS. Проверки: `tests/Feature/UniversalDrivers/ProfileCatalogTest.php` (требуют Composer+тестовую БД CMS). Никаких публичных CRUD-маршрутов в этой итерации нет, чтобы не открывать доступ без полной админской авторизации и аудита (это итерация 7).


## Итерация 7 — каталог драйверов в админке (0.53.9)

В меню **Серверы → Драйверы** появился отдельный интерфейс с вкладками LoginServer и GameServer. Списки включают встроенные и пользовательские профили. Администратор может создать профиль с нуля, задать имя/ID, таблицы и колонки, связи, поля аккаунтов/персонажей (в том числе EAV), фильтры, рейтинги, героев, замки и разрешённые возможности. Импорт и экспорт — через обычный JSON до 256 КиБ. Создание и редактирование не подключаются к игровой базе.

Встроенный профиль можно редактировать без перезаписи файла в поставке (локальная редакция в БД CMS), скрывать, экспортировать и восстановить исходный вариант. Подключённые/проверенные профили удалить нельзя. Если два администратора одновременно изменяют один профиль, устаревшее сохранение отклоняется. Вносить изменения могут только администраторы с `servers.manage`; аудитору доступен просмотр и экспорт. Действия отражаются в журнале аудита без содержимого JSON.

**Ограничение:** это редактор и каталог, не включение новых драйверов для живых LoginServer/GameServer. Выбор пользовательского драйвера в обычной форме подключения и проверенные снимки ещё не связаны с ней; это итерация 8. Новые JSON-профили сами по себе не подтверждают работоспособность конкретной игровой сборки. PHPUnit/браузерные/реальные MySQL проверки требуют отдельного запуска.
