# Эксплуатационные инструкции

Здесь описаны восстановимые сбои production-установки. Перед ручными изменениями сохраните `.env`, базу CMS, публичные uploads, собственные игровые изображения и журналы обновления.

## Прерванное обновление Windows

Windows Updater создаёт pending-маркер и перемещает устаревшие файлы в версионную резервную копию до изменения маркера установленной версии. Пока обновление не завершено, эти данные являются частью восстановления и удалять их нельзя.

1. Откройте самый новый `storage/logs/update-*.log` и найдите первый неуспешный этап.
2. Не изменяйте `.env`, `storage/app/kaevcms/pending-update.json` и `storage/app/kaevcms/update-backups/`.
3. Повторно распакуйте тот же полный патч либо более новый поддерживаемый патч поверх проекта с заменой файлов.
4. Запустите apply-скрипт из распакованного релиза:

   ```powershell
   .\deployment\windows\apply-<version>.ps1
   ```

5. После успешного обновления выполните:

   ```powershell
   .\deployment\windows\quality.ps1
   .\deployment\windows\browser-quality.ps1
   ```

Не копируйте старые `VERSION`, apply-скрипт, `vendor` или `storage` в новый релиз. Не удаляйте pending-маркер ради обхода проверки версии. Если продолжить обновление не удаётся, сохраните журнал и папку резервной копии перед полным восстановлением проекта из заведомо исправной копии.

## Недоступна внешняя база LoginServer или GameServer

Игрок видит безопасное сообщение о недоступности. Пароли, DSN, SQL и stack trace не выводятся. Данные CMS продолжают работать там, где функция не требует обращения к внешней базе.

Проверяйте по порядку:

1. Откройте **Администрирование → Системная информация** и настройки нужного LoginServer или GameServer.
2. Запустите встроенную проверку подключения.
3. Проверьте адрес, порт, имя базы, пользователя, правила firewall, маршрутизацию и TLS.
4. Убедитесь, что выбранный драйвер и профиль схемы соответствуют внешней базе.
5. Восстановите подключение и повторите исходную операцию. Не создавайте вручную связи аккаунтов и записи наград только из-за временной недоступности базы.

Не публикуйте `.env`, пароли БД, полный DSN и необработанный Laravel stack trace. Для поддержки достаточно версии, времени операции, безопасного класса/кода ошибки, ID сервера и журнала без секретов.

## Очередь наград в состоянии `review` или `failed`

Статусы KaevCMS и внешнего обработчика независимы. Статус CMS `queued` подтверждает только наличие неизменяемых строк в `kaev_reward_queue`, но не фактическую выдачу персонажу. Контракт обработчика описан в `integrations/reward-queue/README.md`.

Для `review`:

1. Не возвращайте зарезервированные предметы и не выдавайте их вручную.
2. Откройте **Администрирование → Очередь наград**, выберите нужный GameServer и прочитайте локализованную причину и рекомендуемое действие.
3. Восстановите подключение к игровой базе. Встроенная проверка различает отсутствие таблицы, неверную схему и недоступную БД.
4. Найдите строки внешней таблицы по точному `operation_uuid`/`request_uuid` и сравните каждый `line_number`, аккаунт, персонажа, ID предмета и количество.
5. Нажимайте **Проверить ещё раз** только после восстановления соединения. Полное совпадение переводит операцию CMS в `queued`; подтверждённое отсутствие — в `failed` с возвратом предметов.

Для `failed`:

- `reward_queue_write_failed` означает, что KaevCMS подтвердила отсутствие строк и вернула предметы в веб-инвентарь. После исправления очереди безопасно создать новую передачу.
- `reward_queue_payload_conflict` остаётся в `review`, а не в `failed`, потому что строки существуют, но их неизменяемый состав отличается. Не удаляйте, не исправляйте и не выдавайте данные вслепую.
- внешний статус обработчика `failed` всё равно доказывает, что запись CMS достигла очереди. Такие строки проверяются через `integrations/reward-queue/problematic.sql`; CMS не должна создавать вторую операцию с тем же UUID.

Для связи журналов наград с audit log используйте UUID операции передачи, UUID начисления, ID GameServer, номер начисления и состав предметов. Сохраните журнал приложения и журнал внешнего обработчика. Не передавайте в поддержку пароли БД и полные строки подключения.

## Что сохранить для обращения в поддержку

- версию KaevCMS и имя пакета обновления;
- новый `storage/logs/update-*.log` либо нужный фрагмент Laravel-журнала без секретов;
- UUID операции и ID GameServer/LoginServer, если они доступны;
- точную команду или действие администратора, завершившееся ошибкой;
- подтверждение, что `.env`, uploads, pending-маркер и резервные копии обновления не удалялись.

## Создание игрового аккаунта зависло в `pending` или завершилось `failed`

KaevCMS не удаляет локальную операцию после неизвестного результата LoginServer. UUID, статус, число попыток и безопасный код ошибки находятся в `user_game_accounts`; открытый пароль не хранится. Не создавайте строку `accounts` вручную и не переводите статус SQL-командой.

Показать операции `pending`, которые не менялись минимум пять минут:

```bash
php artisan kaevcms:game-accounts-recover --older-than=300
```

Проверить одну операцию без повторного INSERT:

```bash
php artisan kaevcms:game-accounts-recover UUID_ОПЕРАЦИИ
```

Команда читает LoginServer и действует безопасно:

- совпадающая запись после ранее начатого INSERT переводит операцию в `active`;
- отсутствующая запись переводит операцию в `failed` и не создаётся повторно без явного разрешения;
- несовпадающий пароль или email оставляет `failed` с кодом конфликта и никогда не привязывает существующий аккаунт;
- недоступный LoginServer сохраняет `pending`.

Повторить INSERT разрешается только после подтверждения, что записи нет:

```bash
php artisan kaevcms:game-accounts-recover UUID_ОПЕРАЦИИ --retry
```

Перед `--retry` восстановите подключение и проверьте правильность выбранного LoginServer. Не меняйте `APP_KEY`: зашифрованное доказательство старых `pending/failed` операций станет недоступно. Команда не запускается по расписанию; оператор применяет её только к конкретной проблеме.
