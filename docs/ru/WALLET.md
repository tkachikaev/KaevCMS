# Wallet в ядре KaevCMS

Начиная с KaevCMS 0.48.0 (итерация A1) основная база CMS содержит две таблицы:

- `wallets` — один кошелёк на `users.id`, стартовый баланс `0`, флаг блокировки (управление добавится в A7). Внешний ключ запрещает удалять пользователя с кошельком каскадно.
- `wallet_entries` — неизменяемая по контракту история будущих операций. Предусмотрены глобальный UUID операции, уникальная пара `source`/`source_key`, SHA-256 отпечаток запроса, направление, беззнаковое количество, остатки до и после, ссылка/причина, инициатор и время. Записи нельзя удалять каскадно вместе с кошельком.

При обновлении для **существующих пользователей** создаются кошельки с нулевым балансом. Для **новых пользователей** кошелёк создаётся по требованию движком A2. Отсутствующая строка у нового пользователя сейчас не означает задолженности или ненулевого остатка.

**A3 добавляет защищённый серверный API для доверенных модулей.** Движок A2 остаётся внутренним. Административные операции пока существуют только как API; интерфейс и реальные платежи ещё не включены. Модели `Wallet` и `WalletEntry` не разрешают массовое назначение полей. Это ограничение модели, а не замена прав доступа к БД.

Баланс хранится целым неотрицательным числом монет (`unsigned BIGINT`), не в RUB/USD. Указанный тип не гарантирует проверку знака во всех поддерживаемых СУБД (в частности, SQLite). В A2 строго проверяются положительные целые суммы, диапазон PHP и транзакционные блокировки MySQL/MariaDB.

**Защита данных при rollback:** откат миграции намеренно запрещён, если существует хотя бы одна запись в журнале или ненулевой баланс. Резервная копия БД обязательна перед любым откатом схемы.

Денежные валюты, тарифы «1 монета = X», комиссии и платёжные операторы будут отдельно в модуле Donations (этап B/C). Игровые базы LoginServer/GameServer кошельком не изменяются.

## A2 — внутренний сервис операций

`App\Services\Wallet\WalletTransactionService` реализует `credit(...)` и `debit(...)`. Каждая операция получает существующего пользователя CMS, **положительное целое** число монет, доверенное имя источника (`[a-z0-9._-]`, до 64 символов) и уникальный ключ операции в рамках источника (до 120 ASCII-символов, например UUID заказа). Ссылка, причина и существующий инициатор User/Admin необязательны; изменение их при повторном запросе вызывает конфликт. Защищённый API и аудит добавлены в A3. **Не вызывать внутренний сервис напрямую из запросов игрока.**

Движок блокирует строку пользователя и кошелька на время транзакции, при необходимости создаёт кошелёк, сверяет текущий остаток с последней записью журнала, отказывает при нехватке средств, нулевой/отрицательной сумме, расходовании заблокированного кошелька, переполнении и повторе ключа с другой нагрузкой. Баланс и запись журнала фиксируются атомарно. Входящие начисления допустимы при блокировке. Точное повторение успешной операции возвращает прежнюю запись без новых монет.

Миграции A1 не изменены. Журнал **неизменяем по контракту приложения**, но администратор с прямым доступом к SQL технически может вмешаться. В A3 добавлены полная read-only сверка истории и контролируемый модульный API.

### Проверки

- PHPUnit: `php artisan test --filter=WalletTransactionServiceTest` (по умолчанию тестовая SQLite).
- **Отдельная обязательная проверка конкурентности MySQL/MariaDB:** в одноразовой тестовой БД (название содержит `test`) выполнить миграции и запустить с `APP_ENV=testing`, `WALLET_TEST_ALLOW_CONCURRENCY=1`: `php tests/Integration/Wallet/mysql-concurrency.php`. Тест запускает по десять независимых процессов для списаний и повторных начислений. **Не запускать на рабочей БД.**
- Полные `quality.ps1` и `browser-quality.ps1` подтверждаются отдельно в Windows. SQLite-тесты не заменяют проверки блокировок MySQL/MariaDB.

## A3 — официальный API, аудит и сверка (0.48.2)

Встроенные и будущие модули получают `App\Contracts\WalletGateway` через контейнер Laravel. Прямые вызовы `WalletTransactionService` и SQL-изменения таблиц кошелька **запрещены** для интеграций. Источник — серверный enum `WalletSource`, а не параметр из HTTP. Все источники интеграций по умолчанию выключены в `config/wallet.php`; активация — только доверенным серверным кодом при подключении модуля. Сам модуль обязан проверить владельца заказа и подтверждение оплаты. Любой установленный PHP-модуль является доверенным кодом — физически изолировать его от БД средствами Laravel нельзя.

- `creditFromModule` разрешает лишь разрешённые и явно включённые источники Donations, Promo Codes, Daily Rewards, Shop Refund. Требуются получатель, положительное число монет, стабильный ключ и непустая ссылка на операцию.
- `debitForOwner` предназначен для Shop: нужен активный авторизованный игрок, совпадающий с владельцем кошелька, и включённый источник Shop. Чужой кошелёк, гость или выключенный модуль — отказ.
- `manualCredit`/`manualDebit` требуют реального авторизованного активного Owner/Administrator, разрешения `wallet.manage` и обязательной причины. `wallet.view` закреплено для будущего раздела A6: Auditor видит, но не изменяет, Editor не имеет прав. Это методы сервиса, публичного маршрута начисления нет.

При новом начислении/списании `AuditLogger` записывает событие `wallet` **внутри той же транзакции**. Если запись аудита не сохранилась, изменение баланса и журнала откатывается (`audit_unavailable`). При повторе успешного запроса не создаётся второй аудит. Общий журнал CMS имеет retention, но `wallet_entries` является постоянной финансовой историей и не подлежит автоматическому удалению.

Полная проверка: `php artisan kaevcms:wallets-reconcile` или `php artisan kaevcms:wallets-reconcile --user=123`, необязательный `--limit=100`. Команда проверяет каждую запись, арифметику, непрерывность и совпадение итогового остатка, выводит ID проблемных кошельков и возвращает ненулевой код при нарушениях. **Ничего не исправляет и не списывает.** Привилегированный SQL может подделать всю историю вместе с балансом — это не аппаратно защищённый журнал.

Тесты: `php artisan test --filter=Wallet` и `php artisan test --filter=AdminRoleTest`. Полные Windows gates и гонки MySQL/MariaDB выполняются отдельно. Миграции A1 не менялись.

## A4 — оформление виртуальной валюты (0.48.3)

В админке откройте **Настройки → Оформление кошелька**. Owner/Administrator меняют параметры, Auditor только читает, Editor и гость не имеют доступа. Можно настроить названия на RU/EN с формами `one/few/many` и необязательное короткое обозначение. Для русского используются формы 1/21 «монета», 2/3/4 «монеты», 0/5/11 «монет», исключая 12–14. Для английского используются единственное число при 1 и множественное иначе. `WalletAppearanceSettings` предоставляет `values()`, `forms()` и `label()` будущему интерфейсу игрока A5; сами темы личного кабинета эта версия не изменяет. Настройки не влияют на баланс, финансовые записи и базы игровых серверов.

Иконка загружается через существующие `SettingsImageStorage` / `PublicImageStorage` в `public/uploads/settings/wallet-coin/<uuid>.png|webp`. Только настоящий PNG/WebP с совпадающим расширением, до 1 МиБ и 1024 пикселей по ширине/высоте; SVG, JPG, ICO и PHP запрещены. Путь строго проверяется; новая иконка сохраняется под UUID; прежняя удаляется только после успешной записи настроек. Если иконка удалена или отсутствует, админка показывает встроенный символ монеты. Каталог uploads является runtime и не включается в релиз; родительский `.htaccess` запрещает исполнение PHP под Apache. В nginx отдельно настраивается запрет исполнения скриптов из uploads. Для хранения используется существующая таблица `cms_settings`, новой миграции и Composer-зависимостей нет.

Цены в рублях, долларах, евро и других валютах **не относятся к Core Wallet**: они будут в модуле Donations. В Windows/browser проверках дополнительно проверить форму админки, превью и обновление в standard/split layout. `WalletAppearanceSettingsTest` покрывает права, поддельные расширения/MIME и настройки.

## A5 — кошелёк игрока (0.48.4)

Авторизованный пользователь с подтверждённой почтой может открыть **«Мой кошелёк»** по `/account/wallet` или `/{locale}/account/wallet`. В обеих темах ЛК: пункт в боковом меню, актуальный баланс и своя иконка в шапке и меню профиля, приватная история по 20 записей на страницу. Если у недавно созданного пользователя кошелька ещё нет, отображается ноль без создания фиктивной финансовой записи. При блокировке показывается предупреждение о запрете расходов. Игрок не может начислять, списывать и переводить монеты, инициировать платёж или менять настройки через эту страницу.

История выбирается только по связи с авторизованным пользователем CMS; параметры URL не позволяют выбрать чужой кошелёк. Показываются лишь направление, сумма, дата и остаток после операции. Причина, служебная ссылка, source_key, UUID, fingerprint и идентификаторы администратора скрыты. Игровые базы не используются; новых миграций и зависимостей нет, uploads не затрагиваются.

**Livewire:** боковая панель остаётся постоянной, а верхняя панель теперь перерисовывается при переходах, чтобы баланс и иконка не застывали в состоянии прежней страницы. Это намеренное изменение прежнего контракта топбара; тест `AccountNavigationTest` изменён именно под новую логику, дополнительно создан `WalletPageTest` для двух тем. В Windows принять десктоп/мобильный вид, `quality.ps1`, `browser-quality.ps1`.

Версии тем: `kaev-aurelia` 1.6.8, `luxury` 1.6.6; обе требуют CMS 0.48.4. Пока нет оплаты, ставок валют или модуля Donations.

## A6 — административное управление кошельками (0.48.5)

Раздел **Пользователи → Кошельки** доступен Owner, Administrator и Auditor (`wallet.view`). Поиск пользователя CMS по имени, email и ID, просмотр баланса, блокировки и приватного журнала операций с пагинацией. Со страницы пользователя есть прямая ссылка на кошелёк. Отсутствующий кошелёк отображается как 0 без изменения БД при просмотре. Баланс принадлежит учётной записи CMS, не игровому аккаунту.

Owner и Administrator с `wallet.manage` могут вручную начислять и списывать монеты. Сервер принимает только положительные целые числа без float, направление `credit/debit`, обязательную причину 3–190 символов, явное подтверждение и уникальный ключ формы UUID. Повтор с тем же ключом и содержимым возвращает исходную операцию без двойного начисления, а изменение параметров при том же ключе отклоняется. Существующий `WalletGateway` повторно проверяет права администратора и использует атомарный движок. Недостаток монет, блокировка расходов, переполнение и несоответствие журнала безопасно отклоняются. Записи аудита и изменение баланса находятся в одной транзакции. Auditor только читает, Editor не имеет доступа.

**Ещё не реализовано:** блокировка/разблокировка администратором (A7), валютные тарифы, оплата, возвраты, Donations и Shop. Миграции не изменены, зависимостей и обновления тем нет. Windows `quality.ps1`, `browser-quality.ps1` и реальные MySQL конкурентные тесты ещё требуются в пользовательском окружении.

## A7 — блокировка и постоянная история статусов (0.48.6)

Owner и Administrator (`wallet.manage`) блокируют и разблокируют **расходование монет** в разделе **Пользователи → Кошельки → [игрок]**. Требуются подтверждение, обязательная причина 3–190 символов и уникальный UUID формы. Действие не является денежной операцией: баланс и `wallet_entries` остаются без изменений. Заблокированный кошелёк **может получать начисления**, но не может расходовать монеты через администратора или будущий Shop. Повторное переключение в то же состояние без нового перехода отклоняется. Auditor просматривает историю без возможности изменения, Editor/гость не допускаются.

Новая таблица `wallet_status_events` постоянно хранит смены статуса, инициатора-администратора, причину, время, ключ идемпотентности/отпечаток и значения до/после. В отличие от вторичного `audit_logs`, эта история не удаляется по сроку хранения аудита. Одновременно создаётся стандартное audit-событие; если его запись не удалась, статус и история полностью откатываются. Идентичный повтор с тем же ключом возвращает старое событие без нового изменения, подмена содержимого/получателя отклоняется. Переходы синхронизируются блокировками строк с финансовым движком. При повреждённом журнале разблокировка запрещена; заблокировать подозрительный кошелёк можно.

Миграция `2026_10_15_000001_create_wallet_status_events_table.php` добавляет новую таблицу, не меняет ранее выпущенную миграцию A1, балансы пользователей, игровые базы и журнал монет. Откат при наличии истории статусов запрещён; перед изменением схемы требуется резервная копия БД.

**Приёмка перед Donations (B1):** выполнить `quality.ps1`, `browser-quality.ps1`, wallet PHPUnit, `kaevcms:wallets-reconcile`, MySQL/MariaDB конкурентные тесты в выделенной тестовой БД, чистую установку и обновления, мобильный UI обеих тем, проверку блокировки расходов с разрешёнными начислениями, повторов, гонок block/debit, отказа аудита и защиты runtime. Пользователь пока не подтверждал прохождение этих проверок.
