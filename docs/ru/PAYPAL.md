# PayPal Orders v2 — подключение в KaevCMS

> **Статус версии 0.55.11 (Donations 1.17.11): QA candidate.** Код Live-платежей подготовлен, но его нельзя считать готовым для боевого приёма без проверки полного набора тестов, реальной Sandbox-покупки и отдельного согласованного Live-платежа.

PayPal — независимая платёжная система Donations для владельца сервера с **собственным PayPal Business**. KaevCMS не принимает деньги на свой счёт и не выступает агрегатором. Монеты начисляются в единый Wallet CMS, а не непосредственно на игровой аккаунт.

## 1. Подготовка

1. Установите KaevCMS на публичном сайте с **HTTPS**, настройте основную БД **MySQL/MariaDB** и включите модуль **Пожертвования**.
2. В **Пожертвования → Валюты и цены** задайте курс монет для нужной валюты. Список валют PayPal в настройках формируется как пересечение валют CMS и PayPal с совместимой точностью; произвольный код валюты ввести нельзя.
3. В [PayPal Developer Dashboard](https://developer.paypal.com/dashboard/applications/) подготовьте REST-приложение для **Sandbox** и приложение для **Live**. Для каждого получите **Client ID** и **Client Secret**, для Live — **Merchant ID (PayPal account ID)** получателя.
4. В **Пожертвования → Платёжные системы → PayPal** введите реквизиты отдельно для Sandbox и Live; отметьте доступные валюты. Секреты зашифрованы, обратно не показываются. `.env` для PayPal редактировать не нужно.

## 2. Настройка webhook

1. Скопируйте **URL уведомлений PayPal** прямо из карточки провайдера в админке; укажите его в REST-приложении PayPal Developer Dashboard для нужной среды.
2. Подпишитесь на события `CHECKOUT.ORDER.APPROVED`, `CHECKOUT.PAYMENT-APPROVAL.REVERSED`, `PAYMENT.CAPTURE.PENDING`, `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.CAPTURE.REVERSED`, `CUSTOMER.DISPUTE.CREATED` — в зависимости от доступности событий для вашего приложения. Проверяйте список в интерфейсе PayPal и официальной документации.
3. Сохраните **Webhook ID** отдельно для Sandbox и Live в настройках CMS. Это именно **ID webhook**, а не адрес.

Webhook принимает только POST JSON по HTTPS, проверяет подпись PayPal через официальный REST API по исходному телу события и ограничивает запрос 64 KiB. Подписанный webhook сам по себе **не начисляет монеты**: завершённую оплату дополнительно сверяют серверными запросами к PayPal (Order и Capture).

## 3. Административная Sandbox-покупка

1. На странице PayPal нажмите **«Проверить реквизиты»** с выбранной средой Sandbox. Успешный OAuth-тест подтверждает доступ к API, **не** работу webhook и не возможность принять Live-платёж.
2. В разделе **Sandbox** выберите валюту и сумму, нажмите кнопку создания тестового заказа.
3. Авторизуйтесь **тестовым покупателем Sandbox**, отличным от тестового продавца, подтвердите заказ в PayPal и вернитесь в CMS.
4. Запустите **Capture** в административном сценарии и убедитесь, что попытка завершилась `sandbox_verified`. Проверьте, что баланс Wallet и история начислений не изменились.
5. Проверьте отправку настоящего webhook из Sandbox и его появление в обработке событий. Симулятор webhook не заменяет реальную доставку и не подтверждает корректность всех подписей.

Этот сценарий доступен только Owner/Administrator. Sandbox **не отображается игрокам** и никогда не даёт начисления Wallet.

## 4. Включение Live и контрольная оплата

До включения Live должны пройти PHPUnit/Feature, MySQL/MariaDB-проверки миграций и конкурентности, проверки старых провайдеров, PHPStan/Pint и браузерные тесты. Для боевого контроля используйте отдельный согласованный настоящий платёж владельца; отсутствие этого шага означает, что production-приёмка **не завершена**.

После приёмки сохраните **Live Client ID, Client Secret, Merchant ID, Webhook ID**, выберите валюты и включите **PayPal Live**. Убедитесь, что соответствующий курс включён, и Donations разрешает платежи всем игрокам. Режим «только выбранный игрок» PayPal не поддерживает.

Игрок переходит на сайт PayPal по ссылке одобрения. **Возврат браузера без подтверждённого Capture не считается оплатой.** После серверной проверки статуса `COMPLETED`, PayPal Merchant ID, суммы, валюты и сохранённых идентификаторов Wallet пополняется **ровно один раз**, в том числе при повторном webhook.

## 5. Неопределённый платёж, возврат или спор

- Если Capture завершился таймаутом, в карточке заказа появляется `requires_review` (требует проверки). Нажмите **«Проверить через PayPal API»**: действие только читает сохранённые Order/Capture ID через GET, не инициирует новое списание. При отсутствии однозначного ответа проверьте транзакцию непосредственно в PayPal Business.
- Подписанные события refund/reversal/dispute привязываются к **уже оплаченному** заказу и исходному Capture; администратор увидит отметку и одно дедуплицированное уведомление Owner/Administrator.
- **Автоматических возвратов, списания монет, блокировок игроков и урегулирования споров нет.** Исходное начисление и статус оплаченного заказа сохраняются; администратор решает вопрос в PayPal вне CMS.
- После смены реквизитов/мерчанта старые попытки без прежнего доступа могут требовать ручной проверки. Не изменяйте реквизиты во время активных платежей без плана восстановления.

## 6. Что проверить при сбое

Публичный HTTPS и маршрутизация webhook; соответствие Sandbox/Live ID и ключей; Merchant ID получателя; курс выбранной валюты; настройки подписки на события и фактическую доставку в PayPal Developer Dashboard; права Owner/Administrator; доступность REST API. Не отключайте проверку подписи и не подтверждайте платёж «на глаз». Не сохраняйте ключи в логах и публичных отчётах.

**Официальные ссылки:** [REST Orders v2](https://developer.paypal.com/api/rest/integration/orders-api), [подписка на webhook](https://developer.paypal.com/payment-methods/webhooks/), [тестирование Sandbox](https://developer.paypal.com/sandbox-testing/accounts).

Использование PayPal для продажи виртуальных игровых монет зависит от правил PayPal, страны и условий мерчанта. Проверить допустимость такого приёма платежей обязан владелец сервера.
