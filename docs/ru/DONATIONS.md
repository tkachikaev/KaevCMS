# Donations C4d — KaevCMS 0.50.6

**Текущая версия Donations 1.10.1**: 60 минут на новый заказ, обработка подлинных поздних подтверждений при истечении/отмене заказа и смене режима провайдера, простые статусы обработки/проверки. Прежний учёт комиссий и ручных споров сохранён; live-платежи и начисления выключены. Описания C1–C4a ниже — история разработки.

## Historical C1 reference


Модуль `Donations 1.5.0`: универсальная архитектура провайдеров. Рабочих платёжных драйверов в этой версии **нет**, реальных списаний денег, webhook или начислений монет **нет**. B5 сохраняет неоплачиваемые тестовые заявки, приватную историю и административный журнал.

## Платёжные системы

Раздел «Donations → Платёжные системы» показывает только установленные в коде CMS драйверы. В 0.50.0 список пуст. В будущих релизах UnitPay и другие драйверы регистрируются через доверенный PHP-allowlist (`DonationProviderRegistry`), а не через произвольные имена классов из БД или HTTP.

Для каждого провайдера отдельно хранятся: включён/выключен (по умолчанию выключен), режим `test`/`live`, выбранные поддерживаемые валюты и зашифрованные реквизиты. Ключи шифруются через Laravel Crypt/APP_KEY, не отображаются в формах, не попадают в штатный аудит и не возвращаются через сервис отображения. Пустое поле реквизита при повторном сохранении оставляет прежний ключ. При повреждённом шифротексте провайдер не считается пригодным для платежей. Храните резервную копию APP_KEY — потеря ключа сделает реквизиты нечитаемыми.

Owner/Administrator могут менять настройки; Auditor — только читать состояние без ключей; Editor запрещён. Настройки и запись аудита находятся в одной транзакции. Валюты и цена **одной монеты** настраиваются в прежнем общем разделе Donations. Ограничений на выбор валют администратором из-за отсутствия провайдера нет. В будущем для оплаты потребуется одновременно поддержка валюты со стороны драйвера, её разрешение у мерчанта и активный тариф. Никаких курсов и автоматических конвертаций.

## Контракт

`Contracts/PaymentProvider.php`: идентификатор, поддерживаемые валюты, возможность тестового режима, перечень полей, проверка конфигурации, создание платежа из серверного `PaymentIntent` и верификация `ProviderCallback` до возвращения доверенного `VerifiedPayment`. Клиентские URL успеха не являются подтверждением оплаты; `PaymentCheckout` предназначен только для перенаправления. Фактический драйвер, проверка подписей, доверенный обработчик webhook, жизненный цикл реальных платежей и выдача монет будут реализованы отдельно в `0.50.1+`.

## Проверка

В меню ЛК при включённом пополнении отображается «Пополнить монеты»: оно ведёт прямо к выбору количества и валюты. История доступна кнопкой «Мои тестовые заявки». Из истории и отдельной заявки можно вернуться кнопкой «Выбрать количество монет». При отключении пополнения пункт меню ведёт в историю, а кнопка создания новой заявки скрывается; старые заявки остаются доступны. Один модуль регистрирует только один пункт меню ЛК, чтобы история не заменяла ссылку на калькулятор.

Калькулятор оформлен скруглённой карточкой в обеих темах. Поле количества и ползунок синхронизированы в пределах настроенных лимитов; стоимость и разложение цены обновляются сразу при изменении количества или валюты без запросов к серверу. Расчёт в браузере использует целые минимальные денежные единицы (`BigInt`), учитывая точность валюты. Некорректное количество убирает прежний итог и блокирует создание заявки. В заявку передаются выбранные количество и валюта; сервер повторно читает тариф и считает сумму. После Livewire-переходов калькулятор инициализируется заново. Без JavaScript остаётся кнопка «Рассчитать» с серверным расчётом.

Настройки Donations редактируются одной формой: видимость в ЛК, лимиты количества монет, цены и доступность всех валют. Кнопка **«Сохранить изменения»** записывает весь набор одной транзакцией. Отдельных кнопок сохранения для валют, лимитов и отображения больше нет. Выбор валюты и «Добавить валюту» добавляют строку в форму; до общего сохранения в базе ничего не меняется. Расчёт примера обновляется на месте без отправки формы, включая нажатие Enter в поле количества.

«Удалить валюту» помечает существующий тариф к удалению. До сохранения доступна кнопка «Отменить удаление»; новая несохранённая строка просто убирается из формы. Удаление применяется только при общем сохранении и убирает тариф из новых расчётов/заявок. Существующие заявки, события, снимки цены/валюты и повтор исходного запроса заявки сохраняются. Можно удалить и последнюю валюту. Платёжные реквизиты провайдеров не изменяются.

При любой ошибке формы или аудита весь набор откатывается, включая удаления; введённые значения и пометки удаления сохраняются для исправления. Настройки защищены снимком состояния: устаревшая вкладка не может перезаписать другое сохранение, в том числе через прежние маршруты тарифов. При конфликте нужно обновить страницу. Старые маршруты одиночного сохранения сохранены для совместимости, но новый интерфейс использует только `PUT /admin/extensions/donations/workspace`.

`DonationWorkspaceTest` проверяет атомарность, роли, отсутствие частичного сохранения, откат при отказе аудита, удаление последней валюты с сохранением истории, повтор старой заявки и защиту от устаревших вкладок. `node tests/browser/run.mjs donations.spec.mjs` проверяет единое сохранение, добавление, удаление/отмену, исправление неверной цены и повторную инициализацию после Livewire-навигации при ширине 1440 и 390 px в одноразовой БД.

Проверено 16.10.2026 без повышения версии 0.50.0: полный `quality.ps1` — 1062 теста, 20 704 проверки, 11 ожидаемых пропусков на Windows; полный `browser-quality.ps1` — 75 успешных браузерных тестов.

- `deployment/windows/quality.ps1`, `deployment/windows/browser-quality.ps1`;
- `tests/Feature/Modules/DonationProvidersTest.php` и прежние Donations/Wallet тесты;
- чистая установка и обновление на тестовой MySQL/MariaDB с проверкой существующих заказов;
- убедиться, что новые реальные payment/webhook URL отсутствуют и никакое изменение настроек не приводит к начислению.

**Важно:** пока нет принятых реальных платежей, модуль можно выключать без потери кошельков. До запуска live-платежей нужен независимый жизненный цикл webhook для ранее созданных заказов, включая ситуацию отключения создания новых оплат.

## C2 — 0.50.1 / Donations 1.6.0 (17.10.2026)

**Актуальная версия:** теперь включён первый доверенный драйвер **ЮMoney для переводов на личный кошелёк** (это не ЮKassa). Поддерживается только RUB. Остальные валюты/тарифы сохраняются независимо, любое число других подключённых драйверов может иметь собственные настройки. Сохранённые реквизиты под Laravel Crypt; уведомления нужно проверять HMAC-SHA256 по `sign` (RFC 3986 + сортировка полей), включая все присутствующие поля, кроме `sign`. Поле `sha1_hash` — устаревшее, самостоятельной аутентификацией не служит.

В `Платёжных системах` можно сохранить номер кошелька, секрет HTTP-уведомлений и (необязательный) OAuth-токен **только чтения** для поиска потерянных уведомлений. Необходимые scopes токена: `operation-history`; не выдавать право `payment`. HTTP URL уведомлений пока **не выдаётся**, потому что C2 не принимает real webhook. `test` обозначает локальную подготовку/тестовые уведомления ЮMoney, **не sandbox перевода денег**. Для отправки формы нужна отдельная завершённая C3-приёмка.

У игрока при наличии включённого тарифа и настроенного ЮMoney появляется кнопка **«Подготовить заявку без оплаты»**. Привязка к заказу однократна, неизменяема, аудируется в транзакции. Берётся **только сумма из серверного заказа**, не браузерная. Драйвер может *рассчитать* POST-поля (`receiver`, `quickpay-form`, `paymentType=PC`, `sum`, `label`, `successURL`), но **не отправляет и не показывает платёжную форму**, поэтому реального движения средств нет. Заказ остаётся `draft`, монеты не начисляются; отмена старого черновика доступна.

**Комиссии:** `withdraw_amount` — списано у плательщика, `amount` — поступило получателю. В подготовке `sum` равен полной фиксированной цене заказа, комиссия относится на владельца. При последующем подтверждении сравнивать с заказом сумму списания, а сумму получения записывать отдельно. Верификация подписи *не означает* начисления: дополнительно обязательны проверка заказа, срока, валюты, получателя, операции, статуса, уникальности и обработка повторов. Тестовые уведомления не должны влиять на production.

`YooMoneyRecoveryProbe` делает read-only запрос `/api/operation-history` с меткой заказа и возвращает только кандидатов `operation_id/status`; не зачисляет монеты и не объявляет платёж завершённым. При ошибке/неполной пагинации — fail closed. C3 потребуется дополнить проверкой `operation-details`, точных сумм, подписей, надёжной историей уведомлений и повторным исполнением через Wallet.

**C2 не готов для денежных платежей.** Нет исполняемого checkout, webhook endpoint, состояний paid/credited, повторной сверки с реальным settlement, обработчика отключённого модуля или возвратов. Миграция C2 аддитивная. Старые миграции и `WalletTransactionService` не менялись. Проверки запускаются на пользовательском Windows/MySQL стенде: `quality.ps1`, `browser-quality.ps1`, clean install/upgrade и race tests. Без сторонних зависимостей доступен `php -d zend.assertions=1 -d assert.exception=1 tests/Integration/Donations/yoomoney-driver-standalone.php`.

Документация провайдера: https://yoomoney.ru/docs/payment-buttons/using-api/forms , https://yoomoney.ru/docs/payment-buttons/using-api/notifications , https://yoomoney.ru/docs/wallet/user-account/operation-history .


## C3 — 0.50.2 / Donations 1.7.0 (17.10.2026)

### Статус: **реальная оплата и зачисление выключены**

- Драйвер ЮMoney и текущие тарифы сохраняются. Игрок по-прежнему может только подготовить заявку **без перехода к оплате**. `config/donation-payments.php`: `callbacks_enabled=false`, `credits_enabled=false`; в `config/wallet.php` источник Donations тоже `false`. Не включать параметры до отдельного C4 и полного QA.
- Обработчик `POST /payments/yoomoney/notify` принадлежит **ядру** CMS и не исчезает при отключении UI Donations. По умолчанию возвращает HTTP 503. Для будущей приёмки проверяет HTTPS (в production), `application/x-www-form-urlencoded`, HMAC-SHA256 по `sign` и immutable `label`, idempotent `operation_id`, точный `withdraw_amount` = зафиксированной стоимости заказа и RUB 643. `amount` хранится отдельно как фактическая сумма зачисления получателю, комиссия может её уменьшить.
- Данные подписанного уведомления зашифрованы через APP_KEY в `module_donation_payment_receipts`; тестовые, неподходящие по сумме, отменённые и повторно оплаченные заказы поступают в журнал/ручной разбор. Каждый заказ может породить **максимум один** `module_donation_payment_settlements` и Wallet-операцию через `WalletGateway` с ключом `donation:<uuid>`. Операция, статус и аудит объединены транзакцией; сбой откатывает все данные и ответ webhook остаётся ошибкой для повторной доставки.
- Позднее подписанное уведомление проверяется и сохраняется даже после закрытия новых заказов; при `cancelled` или `expired` не зачисляется автоматически, а идёт на ручную проверку. Черновик со свидетельством оплаты нельзя отменить кнопкой.
- **Если webhook потерян**: `php artisan kaevcms:donations-reconcile --scan --limit=30` (или `--order=UUID`) использует OAuth-токен только с правом `operation-history` и добавляет неподтверждённые кандидаты в журнал заказа. API истории само по себе не доказывает полную сумму списания и **не может автоматически начислять**. `--retry-verified` повторно проверяет зашифрованные подписанные уведомления, но при штатно закрытых флагах не начисляет. Никакой периодический опрос не включён.
- Смешивание локальной симуляции, тестового `test_notification=true` и продакшен-событий запрещено. `test` не означает песочницу реального кошелька ЮMoney. Нужны отдельная QA приёмка на Windows и MySQL/MariaDB, настоящий merchant-тест (C4) и точная политика комиссий/возвратов.

**Приёмка:** `deployment/windows/quality.ps1`, `browser-quality.ps1`; PHPUnit `DonationYooMoneySettlementTest`, `DonationYooMoneyPreparationsTest`, `YooMoneyDriverTest`; чистая установка и миграция 0.50.1→0.50.2 на отдельной тестовой MySQL. В архиве C3 старые миграции/ядро Wallet не изменены. Не устанавливать и не проверять на рабочей платёжной БД до приёмки.

Для проверки реальной конкурентности на одноразовой MySQL/MariaDB тестовой БД: `APP_ENV=testing DONATIONS_TEST_ALLOW_CONCURRENCY=1 php tests/Integration/Donations/mysql-settlement-concurrency.php`. Не выполнять на production.

Перед установкой Donations на MariaDB проверьте `SHOW GLOBAL VARIABLES LIKE 'explicit_defaults_for_timestamp';`. Опубликованные финансовые миграции требуют явных значений по умолчанию для временных меток: на выбранном сервере БД настройте `explicit_defaults_for_timestamp=ON`. На MariaDB 10.4 с OFF создание `module_donation_recovery_candidates` завершается ошибкой в строгом SQL-режиме. Не изменяйте уже применённые миграции и не отключайте строгий режим ради обхода ошибки. Для отдельного QA-контейнера можно указать `--explicit-defaults-for-timestamp=ON` при запуске, не меняя другой локальный сервер.

Дополнительно выполните `tests/Integration/Donations/mysql-order-concurrency.php` для одновременного создания, отмены и изменения тарифов, а также `tests/Integration/Wallet/mysql-concurrency.php` с `WALLET_TEST_ALLOW_CONCURRENCY=1` для гонок баланса и журнала. Каждый скрипт должен вернуть код 0 **и** итоговое сообщение об успехе; необработанные исключения возвращают код ошибки. После обновления CMS подтвердите ожидающее обновление Donations в разделе **Модули**, затем проверяйте страницы игрока. Это сохраняет явное подтверждение новой версии модуля.

Добавлен защищённый постоянный журнал **ручных сообщений**, не подтверждающих факт возврата или чарджбэка у ЮMoney. В админке Donations → Заявки → конкретная заявка владелец/администратор может привязать запись о споре, сообщении о возврате, чарджбэке, заметке и урегулировании к конкретному нетестовому подтверждению платежа. Детали подписанного подтверждения показывают **точно** `withdraw_amount` (списано у отправителя), `amount` (получено владельцем) и их разницу в RUB без float. Последняя является **фактической разницей**, а не обещанной ставкой комиссии; дополнительных сумм покупателю CMS не начисляет.

Старые 71 миграция и Wallet Core не переписывались, добавлена только миграция `2026_10_17_020000`. **Нет** проверки возврата у провайдера, автоизъятия монет, live checkout или рабочего эквайринга. Все три переключателя начисления/приёма остаются `false`. Прогон `quality.ps1`, `browser-quality.ps1`, чистой установки и обновления 0.50.2→0.50.3 на тестовой MySQL обязателен до признания стабильной версии. В этой версии нет реального checkout и активных платежей. Обязательные тесты: `quality.ps1`, `browser-quality.ps1`, MySQL/MariaDB concurrency, clean install и обновление с 0.50.3, тестовые уведомления провайдера и отрицательные сценарии.

## C4d — 0.50.6 / Donations 1.10.1 (17.10.2026)

- После **успешной проверки HMAC** исходного уведомления CMS сохраняет зашифрованное и защищённое от подмены подтверждение с зафиксированными параметрами платежа. Уже принятый `pending` платёж можно завершить после смены ключа ЮMoney и истечения 24-часового периода старого ключа.
- Повторно сверяются исходный заказ, провайдер, идентификатор операции, валюта, точная сумма списания и сумма зачисления. Иной платёж, подмена ciphertext и неподписанные записи API истории **не имеют права начислять монеты**. Новый webhook со старым ключом после 24 часов всё так же отвергается.
- Ранние записи C3/C4, где хранилось только зашифрованное сырое уведомление, по-прежнему поддерживаются, но требуют доступного подписного ключа; автоматическая миграция финансовых доказательств не выполняется.
- Wallet, миграции, структура БД не менялись. Live checkout и начисления выключены. Обязательна полноценная приёмка Windows/PHPUnit/Playwright/MySQL перед активацией.

## C4c — 0.50.5 / Donations 1.10.0 (17.10.2026)

- При изменении секретного ключа HTTP-уведомлений ЮMoney CMS на **24 часа** сохраняет прежний ключ в шифрованных настройках. Он используется только для проверки подписей **уже подготовленных до смены** live-заказов. Новые заказы проверяются исключительно новым ключом (граница по ID подготовки, без гонки в одну секунду), тестовые заказы никогда не зачисляют реальные монеты. До четырёх предыдущих ключей при последовательных сменах. В административных формах и логах старые ключи не отображаются.
- Это обычная плановая смена ключа, **не режим реагирования на компрометацию**. При подозрении на утечку остановите обработку callback и начислений, проверьте заказы вручную. После 24 часов старую подпись CMS не принимает; потерянный перевод следует искать через read-only API и разбирать отдельно.
- `php artisan kaevcms:donations-reconcile --scan` проверяет сначала **последние** подготовленные заказы, чтобы недавние не оставались за пределами малого `--limit`. Для старой заявки используйте `--order=UUID`; история API — только кандидаты для разбора, автоматическое начисление из неё запрещено.
- Старые миграции и Wallet не изменены. Для выпуска реальных платежей обязательны полный quality/browser QA на Windows, MySQL/MariaDB concurrency, чистая установка и обновление. `callbacks_enabled=false`, `credits_enabled=false`, `enabled_sources.donations=false`; платёжной формы всё ещё нет.
